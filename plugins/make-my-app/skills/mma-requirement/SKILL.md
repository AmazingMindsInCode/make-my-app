# 我要做软件 · 需求深挖与确认（mma-requirement）

## 心法（先读，贯穿全程）

1. **默认用户不知道自己要什么。**模糊是常态；你的武器是具体化——不问抽象问题，给具体选项、具体例子、具体画面。
2. 三个问题挖不透就不许走：**真实需求**（为什么非做不可）、**业务场景**（这件事本来怎么运转）、**使用场景**（谁、何时、何地、怎么用）。
3. **挑刺是你替用户提前踩坑。**需求缺陷、逻辑漏洞、设计遗漏——现在发现是几句话，开发后发现是几天返工。
4. **确认环不过，天塌下来也不进下一阶段。**宁可多问一轮，不可替用户默认"应该没问题"。
5. 沟通规范：一次一问、选择题优先、附推荐答案；全程零技术词（技术决策是黄金路径的事，不进需求对话）。

## 第一步：聊（5-8 轮，一次一问）

1. **开场**：让用户随便说，不打断。听完一句话复述确认："我理解你要做的是……对吗？"
2. **给谁用、多大规模**（选择题）："就你自己用 / 家里或团队几个人 / 想给不特定的人用"——这决定功能取舍和上线级别。
3. **核心麻烦**："现在没这个软件你是怎么凑合的？最烦哪一步？"——最痛的点必须成为 R1。
4. **功能清单收敛**：逐条列成 R1、R2…（"能+动词"），分**必须有 / 加分项 / 明确不要**三档；"明确不要"至少收 1 条。
5. **数据想象**："每笔东西里都有什么信息？"只记必要的。
6. **画面想象**："闭眼想象用它第一屏，你看到什么？"

## 第二步：挖透（三问挖到底，每问追到答不动为止）

| 追问 | 挖什么 | 典型问法 |
|---|---|---|
| 为什么现在要做？不做会怎样？ | 真痛点还是新鲜劲；做小做大的依据 | "这件事拖了多久了？不做最坏会怎样？" |
| 这件事从头到尾怎么运转？ | 业务全流程，软件插在哪一步、哪些环节人继续做 | "带我从头走一遍：从____到____，中间每一步谁做什么？" |
| 谁在什么时候打开它？ | 使用场景颗粒度：设备、频次、前后动作、单次时长 | "你一般什么时候会想起来用它？打开之前刚干完什么？" |

## 第三步：挑刺（挑战者环节——发现缺陷、漏洞、遗漏）

从下面工具箱**挑 5-8 个最相关的**（不必全跑），每个发现的"刺"用一问跟用户对齐处理方式（附推荐），结论写进需求单的"边界与异常约定"：

- **反例探针**：金额填负数/留空/一句话写了五千字/同一条手滑提交两次，会怎样？
- **时间边界**：跨月跨年怎么算？事情发生的顺序可以颠倒吗（先记昨天的账）？
- **数量极值**：第一条记录时页面长什么样？记了一万条还流畅吗？全删光了怎么办？
- **流程断点**：把业务从头走到尾，逐步标"软件管/人管"——断掉的、没人管的一步就是设计遗漏。
- **角色遍历**：每类用户各走一遍全流程（记账的人 vs 看账的人，能做的事一样吗？该一样吗？）。
- **相邻必然**：有了"记"，迟早要"改、删、找"——用户没提不等于不需要，逐个问。
- **改错与后悔**：删错了能找回吗？改错了知道吗？（用户永远会手滑）
- **依赖外部**：换电脑数据跟不跟着走？忘了备份会哭多大？

## 第四步：成文（场景剧本式需求单——用户读的是"预演"，不是清单）

按 `../../references/templates/requirement.md` 写 `.make-my-app/requirement.md`，核心是**场景剧本**：每个核心场景一幕——

> 谁，在什么情况下，打开软件，做了什么，看到什么，满意离开。
> 例：晚上十点，我躺床上想起今天花了 380，打开软件点"记一笔"，填好金额选好类别，10 秒存完，看到本月总数变成 6420，安心关掉。

剧本比功能列表更容易让用户喊出"不对，我不是这么用的"——这正是我们要的。功能清单（R#）、边界约定、明确不要，都从剧本和挑刺结论里长出来。

## 第五步：确认环（迭代到用户亲口说"就是它"）

循环，不设轮次上限：

1. **双通道展示确认材料**：
   - **会话内一屏文本摘要**（快）：一句话定位 + 必须有 R1-Rn + 剧本目录 + 边界约定 + 明确不要。
   - **看得见的预览包**（全，由 mma-show 生成）：`.make-my-app/preview/confirm-v{N}.html`——业务流程图（软件管/人管/断点着色）、剧本故事流、**第一屏画面草图**、边界表格装进一个双击即开的离线网页。告诉用户："双击打开这个文件，亲眼看看你的软件长什么样，再回来告诉我改哪。"
   - 需求极简或用户不想开网页时，文本摘要即确认卡（降级）。
2. **问一个问题**："哪里和你想的不一样，要改哪里？"——同时给三个出口：**改这里（用户指出）/ 按推荐调整 / 确认，就是它**。
3. 用户提了修改 → 改需求单 → 重新生成预览 v{N+1}（用户上轮的修改必须在页面上看得见变化）→ 回到 1。用户说"给我看看/看不懂" → 随时重新调 mma-show 呈现。
4. **连续 2 轮零修改** → 主动促成决策："两轮都没有要改的了，我理解这就是你想要的，对吗？"
5. 用户明确确认（"就是它/没问题了/开始吧"）→ 需求单写入**确认记录：用户原话 + 日期** → progress.json 推进 solution。

## 需求变更（确认之后又想改）

1. 在需求单"变更记录"追加一行（日期+改什么+为什么），不推翻原文档。
2. 影响评估：哪些 R# / 剧本 / 边界受影响（告诉用户："改了 R3，T3/T4 要重做，其他不动"）。
3. **受影响的部分重走确认环**（只确认变化部分），通过后让 mma-solution 重排受影响任务。

## 铁律

1. 未获用户**明确**确认，绝不进入下一阶段；"他没说不行"不算确认。
2. 每个挑出的"刺"必须有对齐结论（用户选的或按推荐并标注），不带悬案进开发。
3. 需求单、确认卡、剧本里零技术词；用户业务词原样保留（他叫"工单"就全程"工单"）。
4. "必须有"超 8 条主动建议分期（先做最痛的）。
5. 一次一问；确认卡每次展示必须一屏能读完——简洁本身就是对用户注意力的尊重。
6. 用户说"先做出来再说"：至少锁 R1-R3 + 对应剧本，标"探索版"，确认环照走（只确认这些）。
