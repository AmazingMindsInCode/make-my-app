# 我要做软件 · 验收与修复闭环（mma-verify）

两条职责：**修 bug 的闭环纪律** 和 **请独立考官验收**。共同底线：没有真凭实据，不说"好了"。

## 沟通规范

- 用户报 bug 时先复述确认："你是说，点了『记一笔』之后页面没反应，对吗？"——复述错了修的就是错的。
- 修复过程不聊技术；修复完成后告诉用户"请你自己再试一下原来出问题的操作"——**用户的亲手复现**是最后一关。
- 验收报告用大白话：每条"通过/没过"，没过的说人话原因。

## 一、修复闭环（用户报问题时，任何阶段都可进入）

固定六步，缺一不可：

1. **复现**：按用户描述把问题跑出来（浏览器/命令行；browser-test 组件在位时优先用浏览器自动化复现并截图留证）。复现不了就再问细节，绝不凭想象修。
2. **定位**：找到原因。eng-pack 在位时按 **diagnosing-bugs** 的系统化诊断循环做（复现→最小化→假设→插桩验证），并把关键证据记下来；不在位用内置流程（读代码+查日志+二分排除）。
3. **修复**：动工。编辑前重新 Read（P4）。
4. **复现验证**：重跑第 1 步的原始故障场景，确认已消失——**这是铁闸**，"应该修好了"不算数（P5）。这个 bug 考卷没抓到 = 考卷漏了：派 mma-spec-tester 给对应任务补一道题（必要时先补一条 spec），让它以后每次都被考到。
5. **回归检查**：跑全量考卷 `node .make-my-app/tests/run-tests.mjs --restart`，退出码 0（或只差用户亲手验的 2）才算没把别的功能改坏；eng-pack 在位时叠加 **code-review** 视角自查本次改动（spec 合规轴 + 质量轴）。
6. **交代**：告诉用户修了什么（人话），请他亲手再试一次；若是防坑清单没有的新坑，修法追加到 pitfalls.md 并按 `../../references/experience-log.md` 记 pitfall 事件（bug 本身另记一条 failure）；遗留不改的登记进验收报告"遗留缺陷"表并说清为什么。

## 二、阶段验收（verify 阶段 / 上线前）

派**独立考官**子代理 `rookie-reviewer`（agents 目录，通过 Agent 工具派发）：

- 交给它：项目路径、需求单路径（.make-my-app/requirement.md）、任务清单及各任务 spec（progress.json）、测试实例开关 `node .make-my-app/bin/server-ctl.mjs`。**不告诉它开发过程的任何对话**——fresh eyes，它没见过怎么做的，只看做出来的对不对。
- 它先跑全量考卷拿到 spec 级结论，再逐条验 R#，按 `../../references/templates/acceptance-report.md` 出报告（pass / fail / blocked + 证据）。browser-test 包在位时，你可以把浏览器自动化的结果随任务参数交给考官当**线索**——这些结果出自开发者之手，考官不能拿它直接判通过（考官不直接开浏览器）。
- 你处理报告：fail → 回 mma-build 修复闭环，修完**只重验失败条目**；blocked → 告诉用户缺什么（如"需要你的手机连同一个 WiFi 试一下"），补齐再验。
- 全 pass（或用户认账的遗留清单）→ 报告落盘 `.make-my-app/acceptance-report.md`，progress.json 推进 ship。

## 铁律

1. 修复没经过"原始场景复现验证"绝不让用户去试——用户当小白鼠是最大耻辱。
2. 布局/样式/尺寸类问题用**程序化测量**（读元素坐标尺寸对比），不信截图目测（P6）。
3. 带中文的测试请求走文件方式发（P7）。
4. 验收考官必须是没参与开发的子代理，禁止自己验自己。
5. 遗留缺陷必须登记且用户知情，不悄悄放过。
