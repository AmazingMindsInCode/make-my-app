# 我要做软件 · 方案选牌与任务/验收清单生成（mma-solution）

两个任务：①给用户 2-3 张"能做的样子"卡片让他选；②选定后产出**任务清单 + 每个任务的验收标准（spec）**——这是后续开发的路标和测试子代理的考卷。

## 一、出方案卡

- 读 `.make-my-app/requirement.md`（**以场景剧本为主线**——每个剧本都必须有页面承接，承接关系上卡），按 `../../references/templates/solution-card.md` 出 2-3 张卡。
- 卡上只有大白话：几个页面、每个页面干什么（对应哪几幕剧本）、要记哪些东西、大概几天、好处、**诚实的妥协**。
- 技术实现（用什么框架、建几张表）是你的内部决策，按 `../../references/golden-path.md` 定，**不上卡、不解释**，除非用户主动问。
- ⭐推荐卡放第一张（一句话理由），但选哪张是用户的事。
- 卡片文字之外，可调 **mma-show** 生成方案对比预览（`option-v{N}.html`：各卡的页面草图并排、差异高亮），让用户**看着画面**选，而不是读文字想象。

## 二、生成任务清单 + 验收标准（spec）——本技能的核心产出

用户选定后，把"必须有"的功能映射成任务，写入 `progress.json` 的 `tasks`，**每个任务必须带 spec（验收标准）**：

```
{ "id": "T1", "reqId": "R1", "title": "记账页面：能添加一笔账",
  "spec": [
    { "id": "T1-S1", "text": "在页面上点『记一笔』，能填金额、日期、类别、备注并保存" },
    { "id": "T1-S2", "text": "填的金额不是数字时，给出提示且不保存" },
    { "id": "T1-S3", "text": "保存后列表里立刻能看到这笔账" },
    { "id": "T1-S4", "text": "关掉软件重新打开，这笔账还在" }
  ],
  "status": "todo" }
```

**spec 写作规范**：
1. 每条用用户视角的"做了什么→看到什么"描述，零技术词（不写"调用 /api/bills 返回 200"，写"保存后列表里立刻能看到这笔账"）。
2. 每个任务 3-6 条：正常路径 1-2 条 + 出错路径 1 条 + 持久/边界 1 条（如"重新打开还在""空输入不让存"）。
3. spec 是考卷的出题依据：测试子代理（mma-spec-tester）把每条写成能反复跑的考题，所以每条必须"看得见结果"（页面变化/提示/数据仍在），写不出可验证结果的条目要改写。"重新打开还在"会被写成自动重启验证的持久题；颜色、位置、手感这类只能请用户亲手验，尽量少写。
4. **每条带编号 `T#-S#`**，考题按编号对上号。编号一经生成不再复用：删掉的条目编号作废，新增的往后排。
5. 加分项任务排后面，标 `"optional": true`。
6. 用户确认任务清单（一次一问："这 7 个活，按这个顺序做行吗？"👉 推荐：按清单顺序）后才进入开发。

## 三、完成判定

- decisions 里记录了选定的方案卡。
- tasks 全部生成且每条带 spec，已获用户确认。
- progress.json 推进到 env-setup（有缺件时）或 scaffold。

## 铁律

1. 方案卡的妥协必须诚实，不藏短。
2. spec 没写或写不成可验证形式的任务，不准进开发。
3. 需求变更重来时：已完成且不受影响的任务原样保留，受影响的重写 spec 并向用户说明影响（"改了 R3，T3/T4 要重做，T1/T2 不受影响"）。
4. 任务粒度：每个任务 = 一次"做给你看"能展示完整价值的最小单位（半天到一天），拆太碎用户看不到进展，拆太大风险高。
